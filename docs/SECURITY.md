# YourNAS — Security Model (Phase 0)

Status: Phases 1-4 are implemented (startup validation and logging redaction, authentication §3, the file API §6, sharing, permissions, admin and audit §4/§7; Phase 4 has had its security and reviewer pass, see §11). Network exposure (Phase 5) is still design. Passing tests are never treated as proof of security (see Phase 9).

## 1. Assets and threats

| Asset | Threat | Primary control |
|---|---|---|
| Users' files | other user reads/writes them | server-side authorization on every request |
| Windows filesystem outside storage root | path traversal, junction/symlink escape | `storage.resolve` (ARCHITECTURE §7) |
| Credentials | theft, brute force, leakage in logs | Argon2id, login throttling, log redaction |
| Sessions | theft, reuse after logout | opaque tokens stored hashed, expiry, revocation |
| Host | SMB/RDP exposure, privilege escalation | loopback-only backend, low-privilege service account, firewall untouched |
| Availability | disk full, huge uploads, slow clients | size limits, free-space check, request limits |

Out of scope for MVP: an attacker with local administrator access on the server, a compromised friend device that holds a valid session, and nation-state adversaries.

## 2. Mandatory rules (from the PRD, kept verbatim in intent)

1. SMB 445 is never exposed publicly. Current state (verified read-only): port 445 listens on all interfaces, but there is no enabled inbound allow rule for it, and the Ethernet profile is Public. Do not enable File and Printer Sharing on Public networks. Phase 5 re-verifies from an outside vantage point.
2. The Windows firewall stays enabled. It is never disabled to make something work.
3. No plaintext passwords; no hardcoded secrets; secrets never committed.
4. Passwords and tokens are never logged.
5. All authorization is server-side and fails closed.
6. All client-supplied paths are validated; the filesystem is only reached through the storage layer.
7. Uploads are size-limited; malformed requests are rejected safely.

## 3. Authentication

- Argon2id (`argon2-cffi`) with parameters recorded alongside the hash; rehash on login when parameters are raised.
- Login: identical error for unknown user and wrong password, per-account and per-IP exponential backoff (counters persisted to SQLite so a restart does not reset them).
- Account creation: owner only. The first owner is created by a local CLI command (`python -m yournas create-owner`), never by an HTTP endpoint. No public registration.
- Sessions: 256-bit random token, returned once, only its SHA-256 stored. Sliding idle timeout plus absolute lifetime. Logout and password change revoke. Owner can revoke any user's sessions.
- Transport: HTTPS via Tailscale Serve. The backend refuses to bind a non-loopback address unless an explicit, logged override is set.
- Because tokens travel in the `Authorization` header (not cookies), classic CSRF does not apply. If the web client later uses cookies, revisit (SameSite, CSRF token).

### Implemented in Phase 2 (facts, see `docs/API.md` for the contract)

- Hashing: Argon2id with the argon2-cffi defaults (RFC 9106 low-memory profile: t=3, m=64 MiB, p=4); parameters live inside each stored hash and a login re-hashes when they are raised. An unknown username still costs one hash verification, so timing does not reveal which usernames exist.
- Policy: 12–128 characters, not blank, not equal to the username. Login and password-change inputs are length-limited before any hashing.
- Enforcement is fail-closed through FastAPI dependencies (`require_user`, `require_owner`). Any missing, malformed, unknown, expired, revoked or disabled-user token is 401; a non-owner on an owner route is 403. A test lists every route in the OpenAPI schema and requires 401 for each one except `/health` and login, and another test pins the exact route set, so a new unauthenticated or account-creating route fails the suite until it is added on purpose.
- Storage: users and sessions in SQLite (WAL) in `<storage_root>/.yournas-data` (or `data_dir`). It is not reachable through any space. Sessions keep only the SHA-256 of the token. At most one owner row can exist (partial unique index). The audit table (§4, §7) records admin changes and share-space file events only; authentication events go to the JSON log (login_success, login_failed, login_throttled, logout, password_changed, password_change_failed, owner_created). A failed login logs the user id only when the account exists; an unknown username is never logged because people sometimes type a password into that field.
- Throttle: every attempt is charged to the account key and, when known, the address key *before* the password is checked, so a parallel burst gets exactly the allowance. 5 free failures per account, 20 per address, then 15 s doubling to a 15 min cap; locked attempts are refused without being charged, so hammering does not extend a lock. Counters are in SQLite and survive restarts; they decay after 24 h.
- Client address: uvicorn `proxy_headers` stays off. The app takes the TCP peer as the address. A loopback peer (which is what Tailscale Serve will look like) is treated as *unknown*, so it gets no per-address throttle, because one shared bucket would let a single attacker lock every friend out. With `trust_forwarded_for=true` and a loopback peer, the last `X-Forwarded-For` entry (the one the proxy appends) is used; the header is ignored for any non-loopback peer. Enable the flag only in Phase 5, after confirming that Tailscale Serve sets the header.
- Bootstrap: `python -m yournas create-owner` reads the password from the console only (never from arguments or environment), refuses if an owner exists, and validates the storage root first.

## 4. Authorization

See ARCHITECTURE §6. Test matrix (Phase 4): Owner, Friend A, Friend B against own private, others' private, granted share, ungranted share, for read/list/download/upload/mkdir/delete. Every cell is an automated test.

Implemented in Phase 4 step 2b (`tests/test_file_authz.py`, 147 tests): every file and upload route calls `permissions.authorize` first, before the client path is parsed and before the disk is touched (default deny, grants read from the database on every request, a failure while deciding is a denial). No access is the generic 404, identical to an unknown or malformed space; read-only access to a write action is 403. A denied request creates no folder or file. The owner role grants no file access. An upload is bound to the space it was created in and is re-authorized on every request except abort (lookup, before the chunk is written, before the file is moved into place), so revoking or lowering a grant, deleting the share or disabling the account stops it with nothing written. Share-space file events are audited (§7); the audit row of a delete or an overwrite is committed before the action and a failure stops it.

Implemented in Phase 4 step 3 (`tests/test_admin_api.py`): every `/api/v1/admin` route is owner-only (router-level `require_owner`; friend 403, anonymous 401; forged `X-User-Id`, role or id fields change nothing and unknown body fields are refused). The acting user is always the session's. The owner account cannot be disabled or reset, no route creates an owner or changes a role, and there is no user delete. A temporary password appears only in the response that creates or resets it (`no-store`) and in no log or audit row. Shares are created by the server: the client sends a display name, never a path, so a share cannot point outside `shared/<id>`; names are unique ignoring case in every script. Every admin change commits with its audit row, or neither happens. Share delete never removes a file: it is refused (409) while the folder holds anything, checks emptiness inside the delete transaction, drops the share's unfinished uploads and removes the folder with a plain `rmdir` only.

## 5. Filesystem isolation

See ARCHITECTURE §7. Additional host controls (documented and applied in Phase 5/8, only after inspecting current ACLs):

- Service account `yournas-svc`, not an administrator, not a member of Remote Desktop Users.
- NTFS ACL: `yournas-svc` modify on storage root and app data; no other standard users.
- Storage root on NTFS (the FAT32 volume H: is rejected at startup with a clear error).
- Startup validation refuses to run if the storage root is missing, not writable, on the system directory, a reparse point, or a network path.

## 6. Uploads and downloads

Implemented in Phase 3 (contract: `docs/API.md`).

- Authorization: every file route depends on `require_user` and then on `permissions.authorize` (§4). The space root comes from that decision (`users/<user_id>/` for `home`, `shared/<id>/` for a share the caller is granted), never from client input; a space the caller has no grant for is the same generic 404 as an unknown path. The owner has no special access to other users' homes. An upload belongs to the user who created it and to its space: another user, or an unknown or malformed id, gets the same 404.
- Paths: every client path goes through `storage.validate_relative_path` and `storage.resolve` (traversal, absolute, UNC, ADS, device names, junction/symlink escape). Syntax errors are 400 `invalid_path`; anything that fails on the disk, including a reparse point on the way, is 404 `not_found` with an identical body. Responses and errors never contain server paths, user input or storage-layer detail (a fixed code table maps storage errors to HTTP). Logs for file events (`folder_created`, `item_deleted`, `upload_created`, `upload_completed`, `upload_aborted`) carry the user id, sizes, path depth and kind, never a name or a path.
- Uploads are resumable and staged: `POST` registers the upload (a row in the `uploads` table and an empty staging file in `.yournas-tmp`, same volume), `PATCH` appends chunks at a client-stated offset, and the chunk that reaches the declared size is flushed and moved into place with an atomic rename (`overwrite` only replaces a regular file, a folder is never replaced). Nothing is visible at the destination before that. The offset of an upload is the real size of its staging file; the database row holds no counter that could drift. Chunks of one upload are serialized by an in-process lock.
- Size limits: the declared size is bounded by `max_upload_bytes` (default 20 GiB), the bytes actually received by the declared size (a chunk that would pass it is refused and nothing is written), and each chunk by `upload_chunk_max_bytes` (default 8 MiB; it is buffered in memory while it arrives and written only when complete). A request body is capped before the framework buffers it: 16 KiB on every route except the chunk route. A user may hold `max_uploads_per_user` (default 8) unfinished uploads.
- Free-space floor: `free_space_floor_bytes` (default 5 GiB) is enforced at two points. When an upload starts it is refused (507) unless the floor stays free after its declared size plus the unwritten rest of every live upload (all users), so parallel uploads cannot all pass on the same free space. Before every chunk it is checked again against the chunk size (507, offset unchanged), so a disk that fills up meanwhile stops the upload at the floor instead of at zero. There is no per-user total byte quota (known limitation, §11); only the bytes of a user's unfinished uploads are capped (`max_inflight_upload_bytes_per_user`, default 50 GiB, 507 `upload_quota_exceeded`).
- Chunk concurrency: a second chunk for an upload that is being written is refused at once (409 `upload_busy`, no waiting thread), and a user may have `max_concurrent_chunks_per_user` (default 4) chunk requests in flight; more get 429 `too_many_requests` with `Retry-After: 1` before their body is read. One slow client therefore cannot pin worker threads or more than a few chunk buffers.
- Log lines never carry paths or file names. Storage and maintenance failures are logged as the error type and the OS error numbers (`errno`, `winerror`) only, with no exception message and no traceback, because an OSError message contains the server path and the file name.
- Filenames: normalized to NFC, length-limited, reserved characters and Windows device names rejected, for upload destinations as well.
- Downloads always send `Content-Disposition: attachment` with an ASCII-only fallback `filename` and the exact name percent-encoded in `filename*` (a quote, CR/LF, semicolon or non-ASCII name cannot break out of the header), `X-Content-Type-Options: nosniff`, `Content-Type: application/octet-stream` and `Cache-Control: no-store`, so an uploaded HTML file cannot run script in the app's origin. File contents are never interpreted by the server. Single `Range` requests are supported; the file handle is closed however the response ends (finished, aborted by the client, or never started).
- Staging files live in `.yournas-tmp`. The startup sweep no longer wipes the directory: it removes entries not modified for `upload_stale_hours` (default 72 h) and any link, so unfinished uploads survive a restart. Upload maintenance (at startup, and at most every 10 minutes when an upload is created) deletes uploads idle for `upload_stale_hours` together with their staging files, and staging files that no upload refers to once they are over an hour old.
- Deleting something that is open elsewhere (a download in progress) is a clean 423 `busy`, not a 500. `recursive=true` never follows a junction or symlink, and the space root cannot be deleted.

## 7. Logging and audit

Structured JSON logs with rotation. Events: login success/failure, logout, upload, download, delete, mkdir, permission denied, user/share admin actions, startup/shutdown, config errors. A central redaction filter strips `Authorization`, `password`, `token`, and cookie values; a test asserts no secret appears in captured logs. File contents and unnecessary personal data are never logged. Server paths are logged to the server log only, never returned to clients.

Audit retention (`audit_log`, `yournas/audit.py`): rows older than 365 days are deleted, and the table is kept at 100,000 rows. Over the cap the oldest FILE events (`folder_created`, `upload_completed`, `item_deleted`: the only rows a friend with `write` on a share can create) are deleted first; a management/security event (`user_created`, `user_disabled`, `user_enabled`, `password_reset`, `sessions_revoked`, `share_created`, `share_renamed`, `share_deleted`, `grant_set`, `grant_removed`, `password_changed`) is deleted only when no file event is left. The daily prune does this in one transaction; in addition every file event trims the oldest file events in its own transaction (at most 100 per write, never the row just written), so a flood cannot grow the table past the cap between prunes. A test pins the classification, so a new action must be classified on purpose. Limits: a table filled by management events alone is only cut back by the daily prune, and the age limit deletes any row after 365 days.

## 8. Information exposure

- `/health` (unauthenticated) returns only `{"status":"ok"}` style liveness.
- Storage free space, DB status, Tailscale state, and version live behind an owner-only endpoint.
- Error responses use generic messages and a request ID; stack traces stay in the server log.
- `/docs` and `/openapi.json` are disabled in production configuration.

## 9. Secrets and repository hygiene

`.gitignore` excludes `.env`, `config.local.json`, `*.db`, `data/`, `logs/`, keys, and build output. `.env.example` is the only committed config template. A secret scan runs before each phase commit.

## 11. Known limitations (initial)

- Single server, single disk: no redundancy, no backup. Data loss on disk failure.
- No end-to-end encryption; the server operator (owner) can read stored files at the OS level. Disk encryption (BitLocker) is a recommendation, not an MVP feature.
- Delete is permanent in the MVP (no trash/versioning). Deletes and uploads are JSON log events (user id, sizes, depth, kind); in a share they are also in the `audit_log` table (ids and counters only, `home` is never audited). A delete or overwrite in a share writes its audit row first, so a delete that then fails still leaves a row (the intent); likewise an overwrite upload leaves an `upload_completed` row with `overwrite` true even when its final move then fails, and the client's retry adds another. Folder creation and plain uploads are audited after the fact: if that write fails it is logged and the action stands.
- QA findings (Phase 4 step 4, `tests/test_phase4_qa.py`, manual mutation run on a scratch copy): the server has no CORS middleware and sends no `Access-Control-*` header on any route; 1000 failed logins give only 401/429 and write no session or audit row (a locked account recovers by itself); no response, log or database row holds a plaintext password or token (the temporary password exists only in its own response). Path safety (updated at Phase 4 finalization): `validate_relative_path` is the syntax layer and `storage.resolve` is now a second, independent layer. `resolve` itself rejects `.`/`..`, separators, drive and stream markers (`:`), control characters and trailing dots/spaces in any component, then requires the final path (missing tail included) to be in normal form and inside the space root, in addition to the per-component `lstat` reparse-point checks. Tests stub the validator out and show that hostile components, a missing component before `..` (`newdir/../../x`) and a junction are still refused; scratch-copy mutations that remove either new check are caught. This does not remove the check-then-use race (a local writer can still swap a directory for a junction between `resolve` and the open; the NTFS-ACL work of Phase 5 closes it, see the storage-root bullet below).
- Phase 4 step 5 review (security agent + independent reviewer, then re-verified by hand): no Critical or High finding. Fixed with regression tests in `tests/test_phase4_review_fixes.py`: log redaction was quadratic on one long word full of keywords (a hostile URL path stalled the event loop; the key part after the keyword is now bounded to 64 characters and matching starts at the keyword); a login that was verifying while an admin disabled the account, reset or changed the password could still get a session (the session insert now checks, in the same transaction, that the account is enabled and the password hash is the one that was verified; a login that merely spans a disable and an enable is a normal login at that moment, and `DELETE .../sessions` only ends sessions that already exist); the login-throttle row cap could evict a locked account (unlocked rows go first); an upload whose destination path is too long was accepted and failed only at the last chunk (now 400 at creation); an `X-Forwarded-For` of `::ffff:a.b.c.d` had its own throttle bucket; the log of an unexpected error carried the exception message (it now logs the error type, OS error numbers and stack frames only). Share names may contain `<` or `>` and are display text: a web client must escape them.
- Phase 4 finalization (owner decisions, after the step 5 review). IMPLEMENTED AND TESTED: `storage.resolve` hardening (see the QA bullet above; `tests/test_storage_resolve.py`, validator stubbed); audit retention that evicts file events before management/security events with a deterministic row cap (§7; `tests/test_audit.py`, 6 scratch-copy mutations caught); upload reservations: an idle reservation expires after 72 h and releases the user's quota, the server-wide free-space reservation and the staging file, on the next create and at startup, and the reservation and its expiry survive a restart (`tests/test_phase4_finalization.py`). The four mutation survivors of step 4 were re-run on a scratch copy and analysed: M09 (the `.`/`..` check alone is redundant: the trailing-dot rule rejects both, so removing it passes 413 related tests; `resolve` now has its own check), M12 and M21 (route-level `Cache-Control: no-store` on the temporary-password responses: the middleware sets it on every response and the tests assert the header on those responses; removing only the route-level line passes the suite, removing the middleware default is caught by `tests/test_app.py`), M18 (malformed share id at the route: the service answers the same 404); none is a gap, so no test was forced. OWNER DECISIONS TAKEN AFTERWARDS (also implemented and tested, see the next bullet): temporary passwords expire after 7 days, and an upload has an absolute lifetime of 7 days. ACCEPTED LIMITATIONS: the owner has no tool to list or abort another user's upload (not added by decision; the 7 day limit bounds how long a reservation can be held, see Upload limits below). PHASE 5: per-address login throttling needs the real client address, which exists only once Tailscale Serve and `trust_forwarded_for` are verified; until then a loopback peer has no per-address bucket (per-account lockout, the 2-slot Argon2 limit, the request body caps and the loopback-only bind are what protect the login).
- Temporary password expiry and upload absolute lifetime (owner decisions, implemented after the finalization above; no schema change, schema stays v3). TEMPORARY PASSWORDS: an account with `must_change_password = 1` can use its password for 7 days after it was issued; `password_changed_at` is the issue time, because `create_user` and `reset_password` set it to "now" together with the flag and `change_password` clears the flag, so nothing new is stored. From the 7 day mark (`now - issued >= 7 days`) `login` answers 401 `temporary_password_expired` only after the password was verified (a wrong password or an unknown name still gets the generic `invalid_credentials`, so this reveals nothing to a guesser), creates no session, does not rehash and leaves the attempt charged to the login throttle; `authenticate` treats a pending session of such an account as invalid (401 everywhere), and `change_password` refuses it too. A reset gives a new 7 day window; a password changed in time is permanent and never expires, and ordinary permanent passwords are not touched. Accounts that already hold an old temporary password (issued more than 7 days ago) are expired at their first login after the upgrade and need a reset by the owner; nothing is rewritten. The temporary password is still server-generated, shown once with `Cache-Control: no-store`, never stored in plaintext, logged or audited (the tests check the expired-login log and response). The owner list endpoint does not show which accounts are expired. UPLOADS: no upload lives longer than 7 days from its `created_at` (`UPLOAD_MAX_AGE_SECONDS`, a constant, not a setting), however often chunks arrive; the idle limit (72 h) is unchanged. Past the 7 days `status`, `append` and the final move answer the generic 404 (`_find` and the check in `_complete`), the cleanup (create path at most every 10 minutes, and at startup) deletes the row and the staging file and so releases the user's quota and the server-wide reservation, and the owner of the upload can still discard it at once. A finished upload has no row, so a finalized file is never touched; `created_at` is stored, so the limit survives a restart. The cleanup runs on a timer, so an expired but unswept upload can keep its quota for up to the 10 minute interval although it can no longer be used. Tests: `tests/test_temporary_password_expiry.py`, `tests/test_phase4_finalization.py`; scratch-copy mutations of every new check are caught.
- Share delete races: a write that passed its own authorization a moment before the share was deleted can still land in the folder; the folder is then left behind unreferenced (logged `share_dir_orphaned`, id only) and no file is lost. Granting access to a disabled account is allowed (it has effect only once enabled). The owner account cannot be reset over HTTP, and no console reset command exists (owner decision).
- Access changes apply to the next request. A download that is already open may finish after the grant is revoked; an upload cannot (every chunk and the final move are re-checked). The rows and staging of an upload that lost access stay until the user aborts it or the 72 h sweep removes them.
- No 2FA in the MVP.
- Local attackers with write access to the storage root bypass application permissions.
- Log redaction is pattern based (keys such as password, token, secret, authorization, cookie; Bearer/Basic values; URL credentials). It cannot catch a secret written in free prose. Never pass secrets into log messages deliberately.
- Storage-root validation and preparation are separate steps; a local attacker who can swap directories between them is out of scope (see ARCHITECTURE §7).
- Host-header allowlist (Phase 5.1.1, 2026-10-13; tests in `tests/test_host_validation.py`). Defence against DNS rebinding and against being reached under an unexpected name: a page on another origin that is rebound to the loopback address still sends its own name in `Host`. `HostValidationMiddleware` (`core/middleware.py`, parsing in `core/hosts.py`) sits just inside `RequestContextMiddleware`, so it runs before routing, the body limit, the UI headers and authentication, and covers every route (`/app`, `/app/s/*`, `/docs` if enabled, the API, 404 and 405 paths). It accepts `localhost`, `127.0.0.1` and `[::1]` always, plus the exact names in the setting `allowed_hosts` (`YOURNAS_ALLOWED_HOSTS`, default empty = loopback only; no wildcards, no suffix matching, no ports in the setting; names are lower-cased and an IPv6 address is bracketed). A port on the header is syntax-checked (1-65535) but not compared. Anything else is 400 `invalid_host`: a missing Host, more than one Host header, a value with a space, control character, non-ASCII, userinfo, path, trailing dot or more than 255 characters, an unlisted name, and a numeric look-alike such as `127.0.0.2`. Only the `Host` header is read: `X-Forwarded-Host`, `Forwarded` and the like are never used, and `trust_forwarded_for` does not relax it. The rejected value is never echoed or logged (`host_rejected` carries a reason code only); a refusal is checked before any login attempt is counted, so bad-Host requests cannot feed the login throttle. Not covered: this is not authentication, and a client that sends an allowed name is not blocked by it (a local process can send `Host: localhost`). UNVERIFIED and open: which `Host` Tailscale Serve sends to the loopback backend (the Serve header test of Phase 5 must record it), and the exact MagicDNS name, which must be added to `allowed_hosts` before Serve is switched on, or every request through Serve will be refused. HSTS is not part of this change.
- Account lockout can be abused: anyone who can reach the login endpoint can keep a known account locked (each lock at most 15 min) by guessing at it. Accepted because the service is tailnet-only and the alternative is unlimited guessing. Until Phase 5 there is no per-address throttle for loopback peers (see §3).
- No password recovery path for the owner: a forgotten owner password needs a local reset command, which does not exist yet (decision for the owner; the owner can still change it while logged in).
- A session token is a bearer credential: anyone holding it is that user until it is revoked or expires. There is no device list or "log out everywhere" endpoint yet (password change revokes all other sessions).
- Web UI (`/app`, `server/yournas/web/`, pulled forward from Phase 6; see the ROADMAP note). It is plain static files with no build step and no third-party code, served from the same origin as the API. The page keeps the session token in `localStorage` (so a phone stays signed in), which any script running on this origin could read; the protection is a strict `Content-Security-Policy` on every response under `/app` (`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, plus `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-cache`) and a UI that never builds HTML from server data (file and share names are set with `textContent`). `tests/test_web_ui.py` checks the headers, that API responses do not carry them, that the files contain no inline script or style, no outside URL and no `innerHTML`/`eval`, and that every error code the JavaScript branches on exists in the backend. The bearer-token header means no cookies, so no CSRF. These headers cover the UI only; the Phase 5 decision on API-wide frame/CSP headers is unchanged (the Host allowlist is done, see above). The UI marks sample data it shows for things the server cannot report yet (tunnel, DNS, TLS, SMART, backup, private IP, CPU, memory, temperature, drive health, device list, share links) with a `MOCK` tag (`web/static/js/mock.js`); those rows read `SAMPLE`, not `OPERATIONAL`, and the Status summary counts only the live checks (API, database, disk); its REVOKE buttons are disabled. Reviewed after the commit by a security pass (real server on loopback, raw sockets, no Critical or High finding) and an independent reviewer pass; the valid findings were fixed with tests: an unauthenticated 500 without the UI headers for path names the filesystem refuses (now 404 with the headers), UI headers skipped behind a `root_path`, a Status poll from a background tab keeping an owner session alive (it now polls only while visible), two tabs sharing one stored token (a `storage` event restarts the app), and the upload client (see ROADMAP Phase 6). Known and accepted: the token in `localStorage` is a full-session credential if any script ever runs on this origin (CSP and `textContent`-only DOM are the protection; Trusted Types, COOP and CORP are cheap later hardening); downloads are held in browser memory (refused above 512 MiB, because a bearer token rules out a plain link and a streaming download needs a server-issued one-time ticket); the server accepts zero-width and bidi-mark characters in file names, so look-alike names are possible and cosmetic; HSTS is Phase 5 (the Host allowlist was added in Phase 5.1.1, see the bullet "Host-header allowlist" above).
- Request bodies are capped (413, checked on `Content-Length` and while streaming) before the framework buffers them: 16 KiB on every route except `PATCH /api/v1/uploads/{id}`, whose cap is `upload_chunk_max_bytes` plus 1 KiB (the route enforces the exact chunk limit). Chunks are buffered in memory, so concurrent uploads cost up to `upload_chunk_max_bytes` each.
- Upload limits: there is no quota on a user's finished files. A user can hold `max_uploads_per_user` unfinished uploads whose declared sizes add up to at most `max_inflight_upload_bytes_per_user` (default 50 GiB), further bounded by the free-space floor. The floor check counts what ALL live uploads still owe, so one user's declared-but-unwritten uploads (kept alive by one byte per 71 hours, but never longer than 7 days from creation) can make other users' new uploads fail with 507 when free space is within that cap of the floor; the owner can neither list nor abort another user's upload, and disabling a user does not release the reservation until the sweep (72 h idle or 7 days old, whichever comes first). The check and the insert are not one atomic step, so two simultaneous creates can both pass; the per-chunk floor check still protects the floor. Staged bytes are kept until the upload is aborted or goes stale. Listing a folder with about 60,000 entries costs about 0.2 s of CPU per page (the folder is scanned and sorted on every request; the page size does not change that). Chunk locks are per process, so the server must run as one process (enforced since Phase 5 batch 1: the server holds an exclusive OS lock on `<data_dir>/yournas.lock` and a second server on the same data exits with code 3). HSTS is a switch (`enable_hsts`, default off) and stays off until HTTPS through Tailscale Serve is verified. A download is not locked against a concurrent delete or replace: on Windows the delete answers 423 while the file is open; a file replaced mid-stream can end a download short.
- The startup sweep and upload maintenance trust file modification times; a clock set far backwards or forwards can delay or hasten cleanup of staged uploads.
- Argon2 runs (64 MiB each) are limited to 2 at a time process-wide; extra logins queue. Unknown usernames still cost one hash each and, while the client address is unknown (loopback peer, until Phase 5), there is no global login rate limit, so a flood can slow logins down but not exhaust memory. `login_throttle` is capped at 10,000 rows (oldest dropped first).
- A stolen session token can lock the victim out of login for up to 15 minutes by failing `/auth/password` (it shares the account counter). Accepted, same trade-off as above.
- Passwords are not Unicode-normalized: the same password typed with a different composition on two devices may not match. Weak passwords are rejected: fewer than 5 distinct characters, or one of a short list of common 12+ character passwords.
- The database file holds password hashes and is readable by anyone who can read the storage root; Phase 5 NTFS ACLs must restrict `.yournas-data`. `data_dir` must be absolute and not inside `<storage_root>/users` or `/shared`. SQLite runs with `synchronous=FULL` so a power loss cannot resurrect a revoked session.
- The SQLite database is a single file on the same disk as the data. Losing it loses accounts (users must be recreated), not files.
